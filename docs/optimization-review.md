# 项目优化评估

评估日期：2026-10-08。范围：Rust 后端、前端加载与状态管理、配置与文件操作、测试及发布流程。

本文保留优化前的评估结论与当时验证结果。已完成的改动及最新验证见 [优化实施与验证](optimization-implementation.md)。

建议保持现有 Tauri + Rust + 原生 JavaScript 技术栈，先修复功能链路和数据契约，再处理图片加载性能，最后做模块化。此次没有修改业务代码。

## 验证结果与边界

- `npm run test:all`：52 项样式校验通过；14 个测试文件、290 个前端测试通过。
- `cargo test --no-run`：测试程序编译通过。
- 在独立临时工作目录执行 Rust 测试程序：11 项通过。跳过依赖真实网络的更新检查和 Bing 分页测试，避免网络状态影响判断，也避免历史记录测试清空用户真实数据。
- 使用临时 JSDOM 探针执行现有前端函数，复现了图源切换丢失、保存动作调用应用壁纸命令，以及随机候选重试失效。
- 没有测量真实 WebView 的启动时间、进程内存和滚动帧率。下述性能收益是依据实现提出的优化方向，不是已测得的加速比例。

## 第二批：图片加载与启动性能

### 本地画廊：收益最大的优化点

`ui/app.js:1294` 遍历全部图片，每张都 `await read_file_data_url`，后端 `src/main.rs:42` 读取整张文件、编码 Base64，再通过 IPC 返回。卡片串行创建，且本地卡片没有懒加载。初始化在 `ui/app.js:2869` 顺序等待配置、本地画廊、在线列表、历史记录，本地图库越大，其他功能越晚就绪。

建议：

1. 下载或导入时生成约 320–480px 的缩略图，以路径、修改时间和目标尺寸作为缓存键。
2. 使用受限的本地资源协议给 WebView 提供图片 URL，减少 Base64 编码和跨进程字符串复制；进入大图预览时才加载原图。
3. 先显示可见卡片，通过懒加载和有限并发处理缩略图。大图库再引入虚拟列表；不要把所有原图同时放进 `Promise.all`。
4. 配置就绪后，按当前页面加载数据。在线发现和历史可在进入页面时加载，不必等待所有本地原图。
5. 目录扫描、同步文件读写和图像处理放到适当的后台任务；仅把函数改成 `async` 并不能让 `std::fs` 或图像编码自动变为非阻塞。

Base64 本身约增加三分之一编码体积，此外还有进程间复制、字符串和图片解码成本。真实内存峰值需单独测量。

Tauri 官方提供 [`convertFileSrc`](https://v2.tauri.app/reference/javascript/api/namespacecore/#convertfilesrc)；使用时需开启 asset protocol，并只授权应用缓存和用户选择的目录。官方也说明[同步命令默认在主线程执行](https://v2.tauri.app/develop/calling-rust/#async-commands)。

### 在线列表与下载

- `src/downloader.rs:33` 每次操作创建 HTTP Client。改为应用共享 Client，以便利用连接池；API 请求与大图下载分别配置超时。现有统一 8 秒超时可能不适合大文件。
- `src/downloader.rs:550` 整体读取响应到内存。大图下载建议流式写 `.part` 临时文件，限制大小、确认状态与图像格式后再提交最终文件。
- `src/downloader.rs:589` 对所有图片写 `.jpg`，但字节可能是 PNG/WebP。应检测实际格式并选择后缀，或明确转码。
- `src/downloader.rs:55` 的备用预览下载没有检查 HTTP 成功状态或图像有效性，可能缓存错误页面；`ui/app.js:1931` 的 `onerror` 没有一次性回退限制。应拒绝错误响应，回退失败后显示占位并停止重试。
- 在线列表持续追加且保留所有卡片，长时间浏览后 DOM 和图片资源持续增长。先做懒加载、页窗口和资源释放，再根据测量决定是否使用虚拟网格。
- 区分网络失败、限流、没有结果及精选兜底。当前多个图源会把请求失败转换为空列表，前端可能把临时网络问题认作“没有更多图片”。

## 第三批：持久化与边界可靠性

- `src/config.rs:66`、`src/history.rs:26`、`src/downloader.rs:51` 使用相对工作目录。安装启动、开机自启或不同快捷方式可能读取不同配置，也可能遇到不可写目录。使用应用数据/缓存目录；便携模式若需要，则显式识别并迁移旧数据。
- 配置和历史直接覆盖最终 JSON。建议同目录临时文件、适当刷盘及替换；配置损坏时保留坏文件与备份，避免静默覆盖成默认配置。
- 历史记录采用读取—修改—写回，缺少统一协调；应串行化更新并与清空操作协调。下载相同文件也需要按标识去重或加锁。
- `src/main.rs:267` 用 `cmd /c start` 打开未经后端校验的 URL。改用原生打开能力，并在 Rust 层限定 `http/https`；[Windows 的命令解释器会解析特殊字符](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cmd)，不适合接收任意 URL 文本。
- 文件读取、删除命令接受任意路径；下载文件名直接使用 `item.id`。应规范化路径、校验允许目录，生成安全文件名，明确处理路径穿越、同名覆盖和符号链接。
- `tauri.conf.json` 的 CSP 为 `null`。在整理内联脚本/样式和远程图片来源后配置合适的 CSP。
- `src/main.rs:537` 名为 single-instance 的函数只返回普通插件，并没有实例互斥或唤醒逻辑。应实现真正的单实例，减少多进程同时修改配置的可能性。

## 第四批：维护和交付

1. **把测试纳入版本管理和 CI。** `.gitignore` 忽略 `/test`，当前 `git ls-files test` 没有任何结果；发布 workflow 也没有运行测试。克隆仓库后无法依赖这批本地测试。应先跟踪测试，使用 `npm ci`，在 PR 和发布前执行前端检查及离线 Rust 测试。
2. **提高测试真实性。** `test/setup.js` 的保存配置 mock 合并任意字段，而 Rust 只保存声明字段；部分 mock 的返回结构也与真实命令不同。现有名为 E2E 的套件实际是 JSDOM + 模拟 IPC。补少量真实 Tauri/IPC 集成用例，覆盖重启、历史应用、保存不改桌面、慢响应切源和删除失败。
3. **隔离测试副作用。** `src/main.rs:596` 的历史测试会清空当前工作目录下的历史记录。测试应注入临时存储路径；联网测试单独标记并按需运行。
4. **渐进拆分代码。** `ui/app.js` 2873 行，`ui/styles.css` 4420 行。前端拆分 IPC、配置、图库、发现、历史、弹窗、主题与 i18n；后端保留薄命令层，拆出图源、下载、存储及轮换服务。可逐步采用 TypeScript/JSDoc 类型检查，核心价值是明确数据契约。
5. **收敛样式与文案。** 复用组件和主题 token，整理内联样式；动态提示、计数和相对时间仍有中文硬编码，应统一进入 i18n。外部 Google Fonts 的 CSS 导入可改为本地资源或系统字体回退，减少启动对网络的依赖。
6. **整理发布和说明。** 锁定 CLI 版本；对 `Cargo.toml`、`package.json`、Tauri 配置做版本一致性校验。README 的配置示例与真实模型不一致，MIT 链接指向的 LICENSE 文件也未在仓库中找到，应补齐并删去未经测量的性能承诺。

## 推荐实施顺序与验收

**阶段 A：功能可靠。** 统一配置和历史数据契约，拆分下载/应用，修复图源切换、重试和删除结果，实现轮换；同时将测试跟踪并接入 CI。

**阶段 B：性能可量化。** 建立 100/500/1000 张本地壁纸样本，记录可交互时间、首屏图片完成时间、WebView 与 Rust 总内存峰值、快速滚动掉帧和首屏 IPC 数量。再实施缩略图、本地资源协议、有限并发、后台扫描和按页加载，用同一数据集比较前后结果。

**阶段 C：维护成本下降。** 拆分模块、整理样式/i18n、完善应用数据目录、原子写入、下载格式及路径边界。

首批验收应关注用户结果：保存不会改桌面；偏好重启后恢复；最新图源不会被旧响应覆盖；失败候选会继续重试；删除失败会准确反馈；托盘隐藏后轮换仍按配置运行。
